# {{PROJECT_NAME}} 작업 규칙

이 파일은 AI 코딩 에이전트(Claude Code, Codex 등)와 사람이 함께 지키는 규칙입니다.
하위 폴더에 더 가까운 `AGENTS.md`가 있으면 그 범위에서는 그쪽이 우선합니다.

## 1. 시작할 때

1. `docs/continuity/START_HERE.md`와 `docs/continuity/STATUS.md`를 읽는다.
2. `git status --short`를 확인한다. 커밋되지 않은 변경은 진행 중인 작업이다. 지우거나, 덮어쓰거나, 처음부터 다시 만들지 않는다.
3. STATUS의 "마지막 검증"이 지금 소스와 같은 커밋인지 본다. 소스가 바뀌었다면 기록된 검증은 지난 결과다.

## 2. 만들 때

- 필요한 파일만 읽고 가장 작은 유효 변경을 한다. 검증은 위험에 비례한다.
- 없는 도구나 결과를 있는 척하지 않는다. 실행하지 않은 검사는 "미실행"이라고 쓴다.
- 상태는 단계별로 나눠 기록한다: **요청 접수 → 처리 보고 → 실제 관측 → 사용자 수신.** 관측 없이 "완료"로 표시하지 않는다.
- 응답을 기다리는 동안의 빈 값은 "없음"이 아니다. "조회 중"과 "확인 불가"를 따로 둔다.
- 실제 장비·결제·고객 데이터에 영향을 주는 동작은 대상과 시간을 확인한 뒤에만 한다. 기본 자동 테스트는 모의 객체를 쓴다.
- 테스트용 설정으로 만든 결과물을 출시본이라고 부르지 않는다. 빌드, 실기기, 서명, 스토어 심사 결과는 각각 따로 기록한다.

## 3. 배포

- 운영 배포는 `git push`로만 한다. CI가 테스트 → 배포 → 검증을 한다.
- 로컬에서 운영 배포 명령을 실행하지 않는다. `scripts/guard-local-deploy.mjs`가 막는다. 비상시에만 사람이 비상 문구를 직접 넣는다.
- 운영 배포 토큰은 CI 비밀 저장소에만 둔다. 개발 PC와 에이전트 환경에는 두지 않는다. 규칙이 아니라 구조로 막는다.
- 배포 제공자는 하나만 둔다. 두 곳이 같은 push를 배포하게 두지 않는다.

## 4. 완료 조건

아래가 모두 맞아야 "완료"라고 말한다. 에이전트가 끝났다고 보고해도 같다.

- [ ] 관련 테스트가 통과했다 (실행한 명령과 개수를 적는다)
- [ ] 변경이 `{{MAIN_BRANCH}}`에 push됐다 (커밋 SHA를 적는다)
- [ ] 운영이 그 SHA를 서빙한다 (`scripts/verify-deploy.mjs`, 연속 3회)
- [ ] 핵심 화면·경로가 응답한다
- [ ] 사람이 확인해야 하는 것(실기기, 스토어 심사, 실제 장비)은 따로 적었다. 확인 전이면 "미확인"이다

## 5. 비밀값

- 비밀번호, 서비스 키, 서명 키, 고객 데이터는 코드·문서·로그·압축 파일에 넣지 않는다.
- 문서에는 설정의 **이름과 보관 위치**만 쓴다. 예: "`DEPLOY_TOKEN`: GitHub 저장소 Secrets".

## 6. 인수인계

- 대화 기록은 근거가 아니다. 저장소의 소스, 검증 기록, STATUS가 근거다.
- 작업을 멈추기 전에 STATUS에 바꾼 것 / 검증 / 남은 일 / 막힌 것을 적는다. 상태는 증거가 있을 때만 올린다.
- 두 도구나 두 PC가 같은 파일을 동시에 고치지 않는다.

## 7. 보고

끝낼 때 이 순서로 짧게 말한다: 바꾼 것 → 검증(명령과 결과) → 확인하지 못한 것 → 다음 할 일.
